### 2026-09-28 — "Persistent" Mac bug was a stale install

**What happened:** The user reported the notification → Submit → empty-timeline bug as "persistent". `.claude/bug-report-notification-stale-data.md` claimed it was fixed and verified. The running `/Applications/TimeTracker.app` was a 2026-03-12 Debug build with Convex sync; the fix (and all Supabase work) had never been installed. The current code passed the exact repro on the first try.
**Why this was wrong:** The earlier session verified against a DerivedData build and reported "done" without installing into the location the user actually runs. "Verified" meant "works on my build", not "works for the user".
**What better looks like:** For hand-installed apps, "done" includes installing to the user's run location and confirming the running process path. When a user says a bug persists after a fix, first check the running binary (path, mtime, `strings` for a recent symbol) before reading code. Captured in memory `project-mac-install` plus `scripts/install-mac.sh`.

### 2026-09-28 — Stale "no FlowDeck license" memory

**What happened:** Memory said to use xcodebuildmcp. `xcodebuildmcp macos build` failed with only "BUILD FAILED (1 failure)" and no reason. Raw xcodebuild was blocked by the FlowDeck guard. `flowdeck license status` showed an Active yearly plan, and FlowDeck's structured error named the signing problem immediately.
**Why this was wrong:** Memory older than six months overrode the global CLAUDE.md and a hook that both say FlowDeck. The memory had no date or re-check trigger.
**What better looks like:** Deleted the stale memory. When a memory conflicts with a live hook or global instruction, run a 1-second check (`flowdeck license status`) before following it.

### 2026-09-28 — testflight-deploy lane mutates signing and never restores it

**What happened:** `deploy_testflight` calls `update_code_signing_settings(use_automatic_signing: false, code_sign_identity: "Apple Distribution", profile_name: "match AppStore …")` on the working copy. After the local deploy on 2026-07-29, TimeTracker's target stayed on manual signing with an iOS-only profile for every SDK, so all macOS builds failed. That is one reason the Mac fix could never be installed.
**Why this matters:** In CI the checkout is disposable; locally the mutation persists, and the Fastfile comment ("the committed project is never mutated") gives false comfort. Every multi-platform app in the registry is exposed.
**What better looks like:** In the house template, snapshot `project.pbxproj` before `update_code_signing_settings` and restore it in an `ensure` block after `build_app`. Alternatively, pass signing through `xcargs` scoped to `[sdk=iphoneos*]`. Apply once in `~/.claude/skills/testflight-deploy/templates/`, then `scaffold_fastlane.py sync --all`. Not done this session (it touches other apps), so this needs the user's approval.

### 2026-09-28 — axdriver `type` truncates at 20 characters

**What happened:** Typing "<entry B> [verify-freshness]" produced "<entry B, truncated>". `CGEventKeyboardSetUnicodeString` accepts at most 20 UTF-16 units per event, and axdriver sends the whole string in one event. It cost two confusing runs (and briefly corrupted the user's entry, which was restored).
**What better looks like:** axdriver's `type` should chunk text into ≤20-unit events (or one event per character) and report the typed length. Add the limit to the macos-test skill's gotchas. The workaround used: chunk in the caller (`${T[1,20]}` loop).

### 2026-09-28 — zsh builtin `log` shadows /usr/bin/log

**What happened:** `log stream …` in a background task failed with "log:1: too many arguments", because zsh has a `log` builtin.
**What better looks like:** Always call `/usr/bin/log`. Worth a line in the macos-test / macos-development skills.

### 2026-09-28 — FlowDeck guard creates an iOS simulator for a macOS `--help`

**What happened:** `flowdeck run --help` (no `-D`) made the guard create, boot and slim the `cc-1cc6e8dc` iOS simulator for this session, although the saved FlowDeck config targets "My Mac".
**What better looks like:** The guard should skip provisioning for `--help`/`--examples`, and when the saved config targets macOS. The reaper will clean the sim up, but it cost ~10s and RAM.

### 2026-09-28 — `flowdeck run --launch-options` ignored for macOS

**What happened:** `flowdeck run -D "My Mac" --no-build --launch-options='--debug-test-notification'` launched the app with an empty argv (checked with `ps`). The workaround was launching the bundle's binary directly with `nohup`.
**What better looks like:** Note it in the flowdeck skill. For macOS, pass launch args by running the binary directly (or through `open --args` from a script).

### 2026-09-28 — `<private>` error logs

**What happened:** "Failed to refresh from Supabase: <private>" hid the NXDOMAIN reason; I had to find it with dig/curl.

### 2026-09-28 — Negative result read without confirming the input arrived

**What happened:** The first test of `performClick` showed no popover. I concluded the call didn't work and switched to `accessibilityPerformPress()`. The logs later showed that run never logged "Notification tapped": the harness had pressed a stale banner from an earlier launch. `performClick` actually worked, which cost two rebuild cycles.
**Why this was wrong:** A UI test has two halves, input delivery and app behaviour. I read the result without checking the first half.
**What better looks like:** Stream the app log for the whole run and assert that the input-received line appears before interpreting the outcome. Make harness inputs unambiguous (the DEBUG helper now removes its previously delivered test notification).

### 2026-09-28 — Notification harness is intrusive and gets throttled

**What happened:** Each run relaunches the app, taps a banner and pops the popover, taking keyboard focus for ~3s. After ~15 test notifications in ~10 minutes, banners started arriving later than the harness's 10s window. By then the user was switching between Chrome, Cursor and ChatGPT, so the runs were interrupting them.
**What better looks like:** Batch verification runs and say up front "this takes focus for ~30s". Check `lsappinfo front` before each run and pause while the user is active. Give the harness a longer banner wait (20s) and space runs out. Tier-2 automation still steals keyboard focus whenever the app under test activates itself; the macos-test skill should say so.

### 2026-09-28 — SwiftUI MenuBarExtra popover closes after a notification tap

**What happened:** A popover opened with a status item `performClick` (`SwiftUI.WindowMenuBarExtraBehavior.toggleWindow:`) closed again 0.5–1.5s later in 4 of 6 runs, even while the app stayed active and frontmost. `makeKeyAndOrderFront` on the existing window stayed up in every run.
**What better looks like:** Recorded in the project CLAUDE.md gotchas and the `openMenuBarPopover` doc comment. The fix clicks open and shut only to create the window, then shows it directly.
